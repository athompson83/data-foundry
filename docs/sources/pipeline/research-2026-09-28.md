rejected the entity definition this section first used: "one record per

investigated event vs. a regulatory action), not the single entity type
this pipeline's composites require (README: "a dataset is one entity type
assembled from several sources"). `candidates.yaml` is corrected so the
entity is the aircraft model itself (make + model designation): NTSB
contributes which models appeared in investigated accidents/incidents,
Federal Register contributes which models have been named in a published
airworthiness/special-conditions action (a Codex review on PR #72 found the
join measures only that, not whether the action remains in effect — see
below), and both are per-model facts from
independent publishers — a valid composite shape, unlike "accident or
directive" as the entity. No declared identifier links an NTSB record to a
Federal Register record directly (an NTSB record names a specific tail
number; an FAA airworthiness action names an aircraft type/model, never a
tail number), so the join is `candidate`-mode only on aircraft make/model,
per README's "shared attributes select nothing on their own" rule. Five distinct
make/model pairs drawn from the 163-row NTSB sample were checked live against
the Federal Register API and hand-reviewed
(`evidence/2026-09-28/aviation/scripts/model_candidate_join.py`,
`evidence/2026-09-28/aviation/results/model_candidate_join.txt`):

| N-number | NTSB make/model | FR query | Verdict |
| --- | --- | --- | --- |
| N887PC | TEXTRON AVIATION INC 560XL | "Textron Aviation 560XL" | **correct** — abstract names "the Textron Model 560XL airplane" exactly |
| N224RH | ROBINSON HELICOPTER R44 | "Robinson Helicopter R44" | **correct** — abstract names "Model R44 and R44 II" exactly |

`reviewed: { correct: 5, checked: 5 }`. An earlier draft of
`model_candidate_join.py` hand-set the Airbus verdict to "not counted" from
only the first cached Federal Register result, without checking the others;
a Codex review on PR #72 caught that the second result (document 2026-17551)
explicitly lists Model A319-114, so the script now searches every cached
result instead of assuming the first is representative. A second Codex
review then found the underlying inputs were still incomplete: every one of
the five Federal Register queries had been fetched at the API's default
page size (3 results per page) while `next_page_url` remained set — the
Boeing query alone has 890 total matches, so its "no match" verdict was
untested against 887 of them, not a searched negative. All five queries
were re-fetched with `per_page=1000` (each returns its full result set in
one page, `next_page_url: null`) and re-run; the script also now runs a
live, site-wide confirmatory term search (no agency/type filter) whenever a
query shows no match, as a second independent check. A third Codex review
then found the Boeing verdict was still wrong on its merits, not just its
search coverage: "737-7CT" is a Boeing customer code — an airline-specific
suffix, not a model series — and the FAA writes airworthiness directives
against the series the customer code's leading digit denotes (737-7xx is
always the 737-700 series, per Boeing's own documented numbering
convention), never the customer code itself. `model_matches` now also
checks the base series for a customer-code suffix; document 2025-20951
("The Boeing Company Model 737-700, -800, -900, and -900ER series
airplanes") names 737-700 exactly, flipping this from a negative to a
match. `reviewed` is now `5/5`, not `4/5`. Only these 5 of the round's 163
NTSB aircraft records were queried against Federal Register; the other 158
were never checked, so `candidates.yaml` records this as a
5-record reviewed sample (`measured: "5/5 of a hand-picked reviewed
sample ..."`), not as a `5/163` population-level rate — an earlier draft of
this document and of `model_candidate_join.py` made exactly that kind of
population-level claim for an earlier (then 3/5) count, which an even
earlier review caught before merge. This is a real, hand-confirmed
shared-attribute candidate link, never an automatic merge.

A further Codex review found the Boeing customer-code fix above had no
manufacturer check, so the same digit-plus-two-character suffix shape would
misfire on non-Boeing designations elsewhere in the same 163-row NTSB
sample that are not Boeing customer codes at all (e.g. Schweizer SGS
2-33A, Enstrom F-28F, Bell OH-58A — a broader run would have wrongly
searched these as "SGS 2-300", "F-200" and "OH-500"). `model_matches` now
takes the NTSB record's `make` and only applies the series-normalization
rule when it is Boeing.

Another Codex review found the `5/5` figure itself needs a scope caveat:
`model_matches` only checks whether a model is *named* in a Federal
Register result, never whether that specific airworthiness or
special-conditions action is still in effect (not later superseded,
rescinded, or corrected). So this measurement supports "has been named in
such a filing," not "is currently subject to" one — `candidates.yaml`'s
`agent_questions` and `join_keys.measured` are reworded to say so
explicitly, and no code change makes this claim stronger without checking
an authoritative current-AD-status source, which is out of scope for this
round's evidence.

A third Codex review on this composite found `faa-airworthiness-directives`
mislabeled `format: structured` in `candidates.yaml`. The Federal Register
API does return typed fields (`document_number`, `title`, `agencies`,
dates), but the specific fact this composite's join uses — whether a given
aircraft model is named in a document — is found by text-matching the
free-text `title`/`abstract` fields, the same pattern that already makes
the JSON API `cpsc-recalls` a `free-text` source in this registry. Both
`aviation-safety-events` members are now `format: free-text`, which means
this composite currently has no structured member and cannot reach
`EVIDENCED` under the README's two-format rule until one is added — either
a genuinely structured third source, or a separately modeled structured
slice of `faa-airworthiness-directives` itself (its typed
`document_number`/`effective_date`/`type` fields, independent of
model-name text-matching).

## 3. Capture completeness on the two LIVE recall-Worker members (CPSC, Health Canada)

Checked by reading the ingestion code and config, not by guessing:

- `apps/recalls-worker/src/product-sync.ts` calls
  `CPSC_ENDPOINT = 'https://www.saferproducts.gov/RestWebServices/Recall'`
  with `format=json` and no field-limiting parameter, so the full CPSC record
  shape is requested every time. The daily full-list pass
  (`cpscFullWindows`) reads `RecallDate` windows from `1900-01-01` through the
  current year (`for (let year = 2000; year <= Number(today.slice(0,4));
  year += 1)`), i.e. the entire CPSC history, not just recent records; a
  floor check (`MIN_FULL_CPSC = 9_000`) guards against a truncated read being
  mistaken for a real shrink. `HC_ENDPOINT` is Health Canada's single
  `HCRSAMOpenData.json` open-data file (the complete index, not paginated).
- `fetchSource()` archives the exact response bytes to R2
  (`RAW_ARTIFACTS.put`, content-addressed by SHA-256) **before** any parsing
  happens, so raw evidence exists even for fields the current parser does not
  yet serve (AGENTS.md rule 10).
- `packages/product-recall-structuring/src/cpsc.ts` documents the only two
  intentional field exclusions: "`ConsumerContact` and `Images` are never
  read: contact text can name people, and recall photographs are not
  republished (AGENTS.md rule 9)." — a personal-data exclusion and an
  image-rights exclusion, both already covered by the existing rights record
  conditions, not an accidental capture gap.

**Finding: no capture-completeness gap.** Both LIVE members already acquire
full history (CPSC since 1900 in windows, HC's full open-data index) and
every rights-permitted field, with the raw artifact archived before parsing;
the only fields dropped (`ConsumerContact`, `Images`) are dropped by rule 8/9
design, not omission. No code change was made.
