# Fixtures

Golden data for this vertical. Fixtures are a **required** part of a vertical
(AGENTS.md "Vertical requirements": *fixtures/golden records*), and the testing
requirements make them a merge gate: every change must preserve *source fixture
extraction* and *entity-resolution golden tests*.

## Layout

```text
fixtures/
├── <source-key>.<ext>     one artifact per declared source, in its NATIVE format
├── generate-*.ts          generators for binary formats (PDF, XLSX) — commit script AND output
└── golden/
    ├── entities.json      expected canonical entities + aliases
    ├── facts.json         expected facts, including the ones that LOSE selection
    ├── relationships.json expected graph edges
    └── README.md          what each conflict in the fixtures is proving
```

## What makes a fixture set worth having

A fixture set that is clean is worthless — it proves the pipeline works on data
that would never need a pipeline. A useful set is **deliberately messy in
specific, documented ways**:

1. **The same entity from different angles.** Every source describes an
   overlapping slice of the same underlying things, not disjoint data.
2. **The same identifier formatted inconsistently.** Different casing, different
   separators. This is what exercises deterministic identifier normalization
   (AGENTS.md rule 7).
3. **The same quantity in different units.** One source in base units, another
   in domain units, so unit conversion is tested rather than assumed.
4. **Asymmetric coverage.** Each source is missing at least one field another
   source has, so fact merging has something to merge.
5. **At least one genuine conflict.** Two sources that disagree on the same
   property of the same entity, where the resolution is *not* "newest wins" —
   this is what exercises fact selection (doc 04) and conflict retention.
6. **A relationship chain**, not just a single edge, so transitive traversal
   and cycle detection are covered.

If a fixture set has no conflict in it, the fact-selection policy in
`normalizers/fact-selection.yaml` is untested and should be assumed broken.

## Binary fixtures

Formats that cannot be hand-authored (PDF above all) are generated by a
committed script using a library already present in the workspace. **Commit the
script and its output.** The script makes the fixture reviewable and
regenerable; the output makes the test suite runnable without a build step.

## Golden records

`golden/` is the expected canonical output — what the pipeline MUST produce from
the fixtures. Per doc 14 a golden record set specifies identity, critical facts,
relationships, source evidence, display fields and filters.

Golden files are the contract. When the pipeline's output and the golden files
disagree, that is a finding, not a formatting nuisance: update the golden file
only with a reason recorded in `CHANGELOG.md`.
